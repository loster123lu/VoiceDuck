# 虚拟音频设计

## 为什么只需要一组虚拟线缆

普通单线虚拟声卡本身只有播放端和录音端。若把外部音乐软件改到这条线，再将录音端监听到耳机，日常默认设备会被打乱，也容易听到延迟的自己。VoiceDuck 保持所有播放器仍输出到真实耳机，只把最终混音写入虚拟线缆。

实时数据流如下：

```text
所有应用 ─► 真实耳机/音箱 ─► WASAPI 回环 ─► 延迟队列 ─► 回声保护门 ─┐
麦克风 ───────────────────────────────────────────────► 增益 ───┼─► CABLE Input ─► 通话输入
通话应用输出峰值 ─────────────────────────────────────► 控制门 ─┘
```

麦克风从不回放到耳机，因此本机不会听到自己的延迟回听。播放端点的回环数据延迟约 350 ms；通话应用发声后，保护门持续消费但不发送播放数据，并保持到远端语音越过延迟队列。麦克风不经过这道门，始终继续发送。

## 为什么不是只抓音乐进程

Windows 10 build 19045 没有可供普通桌面程序稳定使用的逐进程 PCM loopback 接口。为了兼容 Windows 10，VoiceDuck 捕获所选耳机/音箱上的全部播放声，而不是绑定一个播放器进程。这正好允许网易云、QQ 音乐、浏览器、游戏等任意来源直接分享，但通知音和其他系统声也可能被听到。

微信、QQ 等也没有统一的“远端正在讲话”接口。VoiceDuck 使用 Windows 音频会话峰值识别已知或用户配置的通话应用，并用延迟门阻止远端声音回传。安全优先的取舍是：对方讲话时，正在分享的音乐会短暂消失。未内置识别的通话软件应先加入主界面左侧触发应用。

## 内置驱动边界

VoiceDuck 内置 VB-Audio 发布的标准 `VBCABLE_Driver_Pack45.zip`，保持官方包逐字节不变。它只增加一组端点：

- `CABLE Input`：VoiceDuck 写入混合音频的播放端；
- `CABLE Output`：微信、QQ 等选择的录音端。

驱动安装是可选、明确且可回滚的操作。自动闪避完全不依赖它。VoiceDuck 不会在启动时安装驱动，驱动安装本身不修改默认设备，也不会自动重启。用户启用分享页的“自动切换并恢复系统默认麦克风”后，只有分享运行期间会把三个默认输入角色临时切到 CABLE Output。

自动切换前会记录普通、媒体和通信三个默认输入角色。停止分享、分享异常或正常退出时，仅恢复仍指向 VoiceDuck 所管理 CABLE Output 的角色；分享期间由用户手动改到其他设备的角色不会被覆盖。恢复记录在切换前落盘，异常退出后会在下次启动时再次尝试恢复。

安装前会验证：

- 官方压缩包 SHA-256：`B950E39F01AF1D04EA623C8F6D8EB9B6EA5C477C637295FABF20631C85116BFB`；
- 当前架构安装程序的固定 SHA-256；
- Windows Authenticode 信任结果；
- 签名者名称为 VB-Audio 的发布者 Vincent Burel / BUREL VINCENT。

Windows 10 x64 包内驱动目录由 Microsoft Windows Hardware Compatibility Publisher 签名。VoiceDuck 本身不提供、不修改也不重签内核驱动。

## 为什么安装时必须结束通话

音频驱动的安装和卸载会让 Windows 重新枚举端点。即使不改变默认设备，正在通话的软件也可能在端点变化时短暂丢失音频。因此 VoiceDuck 检测到已配置的微信、QQ、Discord、Teams、Zoom 等音频会话时，会显示预计总用时和最可能受影响的驱动写入阶段，并使用默认选“否”的二次确认。只有用户明确选择继续后才会调用官方安装程序。

驱动安装后如果端点没有立即同时出现，VoiceDuck 只提示稍后手动重启，不会代替用户重启。

## 为什么通话软件仍需首次选择一次

Windows 没有一套能让第三方程序可靠修改所有通话软件内部麦克风设置的公开接口。强行改系统默认麦克风会影响其他程序，也可能重现通话无声问题。因此 VoiceDuck 自动完成驱动校验、安装、端点探测和混音路由，只把 `CABLE Output` 的首次选择留在微信或 QQ 自身设置里。
